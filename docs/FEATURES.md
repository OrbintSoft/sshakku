# Features

What SSHakku promises its users. Each entry is an outcome you can observe from
outside the program — something you could check on your own machine without
reading any source code. The ids are stable: tests, the test matrix, and bug
reports refer to features by id, so a promise and the thing meant to guarantee
it can always be lined up.

This is deliberately *not* a description of how SSHakku works. How it works is
in [DEVELOPMENT.md](DEVELOPMENT.md); what each command does is in
[CLI.md](CLI.md); what you can change is in [CONFIGURATION.md](CONFIGURATION.md).
This page is only the list of claims — the things that, if they stopped being
true, would mean SSHakku is broken regardless of what its code does.

Whether each promise is actually exercised by an automated test is a separate
question, tracked in [TEST-MATRIX.md](TEST-MATRIX.md).

## Agent lifecycle

| Id | Promise | How you can tell |
| --- | --- | --- |
| F1 | Every shell finds a working `ssh-agent` on the same fixed socket, so `SSH_AUTH_SOCK` stays valid even across an agent restart. | `echo $SSH_AUTH_SOCK` names the same path in every shell, and `ssh-add -l` answers in all of them. |
| F2 | A healthy agent someone else started is adopted, never killed. Only a dead agent or a stale socket is cleaned up. | Start your own `ssh-agent` before logging in: its keys are still there afterwards, and its process is still running. |
| F3 | With no keys to load, SSHakku exits cleanly and changes nothing. | An account with an empty `~/.ssh` opens a shell with no error, no delay, and no agent complaints. |
| F50 | Where the system reaches its agent through a named pipe served by a service, rather than through a process listening on a socket, that pipe is the fixed endpoint every shell is pointed at — and each shell is handed it in the writing its own tooling reads: the backslash form where the shell is the system's own, and the slash form where the shell emulates POSIX, which is the only one that survives being carried through such a shell's environment. Both name the one agent, so the shells on a machine share it rather than each reaching a different one. | On Windows, `$env:SSH_AUTH_SOCK` in PowerShell reads `\\.\pipe\openssh-ssh-agent` and `ssh-add -l` answers. In Git Bash on that same machine, `echo $SSH_AUTH_SOCK` reads `//./pipe/openssh-ssh-agent` — and `ssh-add -l` there lists the same keys, because it is the same agent. Set the backslash form by hand in Git Bash instead and `ssh-add` reports no agent at all: that is the spelling this promise exists to avoid handing you. |
| F51 | Where the agent is a service that is not running, SSHakku starts it, and the session that needed it gets a working agent instead of an error. Where it cannot be started — the service disabled, or this account refused — the shell still opens, and you are told once what to run to put it right, with the command named in full rather than described. Where you are told depends on who is there: on the screen of a shell you opened yourself, and in the session log either way — a shell that was handed work to run leaves the line in the log alone, so nothing a script captures changes because SSHakku had something to say. | On Windows, stop the `ssh-agent` service and open a new shell: `ssh-add -l` answers, and the service is running again. Set it to Disabled and open another: the shell opens as usual, one line on screen names the command an administrator can run to enable it, and the session log says the same thing. Run `powershell -Command …` instead, the way a build step does: it exits as it always did, its standard error carries none of this, and the log still holds the line. |
| F52 | Where the system's agent cannot expire keys, your keys still load. They are handed to the agent with no expiry rather than not handed to it at all, and the session log says so: the agent here holds no lifetimes, so the `key_lifetime` you configured is not that agent's to keep. It is still kept — by SSHakku, which is F53 — and `sshakku doctor` lists each key with the time it has left rather than with a deadline the agent would not honour. | On Windows, leave `key_lifetime` at its default and open a shell: `ssh-add -l` lists your keys, and the session log holds one line saying the agent here holds no lifetimes. `sshakku doctor` names it too, and gives each of those keys a remaining time. |
| F53 | A key does not outlive the `key_lifetime` you configured, even where the agent it was handed to cannot expire anything. Every new shell session takes out of the agent the keys whose time has passed, counted from when SSHakku added them, and the session log names each one it removed. Only keys SSHakku added are ever removed: one you added yourself is not SSHakku's to take away, whatever its age. What this cannot do is expire a key at the stroke of its deadline — on such a system the key goes when the next session opens, so a machine nobody logs into keeps it until somebody does. | On Windows, set `key_lifetime = "1m"` and open a shell: your key loads and `ssh-add -l` lists it. Wait a minute and open another shell: `ssh-add -l` no longer lists it, and the session log names the key it took out and how long it had been there. Add a key of your own with `ssh-add` before that second shell, and it is still listed afterwards. |

## Passphrases and the wallet

| Id | Promise | How you can tell |
| --- | --- | --- |
| F4 | The first time a key is used you are asked for its passphrase once, and it is saved in the OS secret store. | The prompt appears exactly once; afterwards the entry exists in your keychain/wallet under the key's name. |
| F5 | Every later login shell loads that key silently, with no prompt. | Log out and back in: `ssh-add -l` already lists the key and nothing was typed. |
| F6 | After a key expires from the agent, the next `ssh` **in a shell that is already open** gets the passphrase from the wallet, with no prompt. | Wait out the key lifetime (or run `ssh-add -D`) without opening a new terminal, then `ssh` to a host: it connects silently. |
| F7 | The passphrase never travels through an environment variable, a command line, or a file on disk. | `ps` and `/proc/<pid>/cmdline` never show it while a key is being added; no file under the runtime directory contains it. |
| F8 | A wrong passphrase is retried a bounded number of times, then that key is left alone until the retry window passes — no repeated prompting in every new shell. | Answer wrong until it gives up: you are asked the configured number of times, told once that the key could not be loaded, and new shells stay quiet. |
| F9 | `sshakku forget` removes stored passphrases, and the next use asks again. Where the wallet gives SSHakku no way to delete, it says so and names the entry for you to remove yourself — it never reports a passphrase as forgotten while it is still stored. | After `sshakku forget <key>`, the wallet entry is gone and the following load prompts; with a wallet that cannot be deleted from, you are told which entry to remove and nothing claims otherwise. |
| F29 | You are asked for a passphrase wherever you can actually answer: in a dialog when your session has a screen to put one on, and on the terminal when it has not — logged in over SSH, or booted into single-user mode. A window with nowhere to appear is never waited on. | Sitting at the machine, the prompt is a dialog. `ssh` into that same machine and load the same key: you are asked on the terminal, straight away, instead of the shell hanging on a dialog you could never have seen. |
| F38 | Closing a passphrase dialog without answering is itself an answer, and it costs you nothing: no passphrase is stored, no key is given up, and the next login shell asks you again from the start — as does `ssh` the moment you use one of those keys. By default that one gesture ends the asking for the rest of the login, so shutting a window you did not ask for does not leave you with one more of them per key. `on_dismiss` decides it: `"skip"` if you would rather turn down one key and still be asked about the others, `"retry"` if closing the dialog should count as a wrong answer and keep asking until the attempts run out. Closing the input on a terminal — Ctrl-D — is that same gesture, and neither one is ever reported to you as a failure. | With three passphrase-protected keys and nothing in the wallet, open a login shell and close the first dialog: no second one appears, `ssh-add -l` lists nothing, and you are told of no error. Open another shell and you are asked again, starting from the first key. Set `on_dismiss = "skip"` and do it again: the other two keys are still asked for. Set `on_dismiss = "retry"`: the same key comes back, and after the configured number of attempts you are told once that it could not be loaded. Press Ctrl-D at a terminal prompt instead of closing a window and the outcome is the same. |
| F24 | A wallet that can only be opened with a password of its own asks you for it, once, rather than failing the shell — and being asked is the exception: a wallet already open never asks. | With KeePassXC closed you are asked for the database password and the key still loads; with KeePassXC open and unlocked, the same key loads with nothing typed. |
| F39 | A wallet that can only be opened where there is a screen is used wherever there is one; where there is none — a machine you reach over SSH — your keys still load. You are asked for each passphrase and the key is added to the agent, and nothing is saved: the next login asks again, as does the next expiry. What such a wallet needs a screen for is being set up, not being used — a compartment it already holds goes on working with no screen at all. | On a machine with no graphical session, with GNOME Keyring as your wallet and no SSHakku compartment in it yet: the login asks for the passphrase once and `ssh-add -l` then lists the key; `ssh-add -D` followed by `ssh-add` asks again rather than reloading silently. Make that compartment once from a desktop session on the same account, then log in with no screen again: the passphrase is saved on first use and later logins load it with nothing typed. |
| F54 | Where the system keeps a wallet of its own that SSHakku can read and write, your passphrases go into that one rather than into something SSHakku brought with it, and a key loads there with nothing typed exactly as it does anywhere else: asked for once, saved, silent at every later session, and taken back out by `sshakku forget`. On Windows that wallet is the Credential Manager, and it is what is in force where your configuration names none. What it has not got is a lock of its own, and that belongs in the promise rather than under it: you are never asked to open this wallet, because your Windows sign-in is the whole of what guards it — so any program running as you can read what SSHakku stored there, where a wallet that locks would have asked first. `sshakku doctor` says as much in as many words, rather than naming a wallet and leaving you to assume another one's guarantees. | On Windows, load a passphrase-protected key: you are asked once, and `cmdkey /list` afterwards lists a generic credential whose name begins with `SSHakku-Key-`. Open a new shell and `ssh-add -l` lists the key with nothing typed. `sshakku doctor` names the Credential Manager and what guards it; `sshakku doctor --test-backend` stores, looks up and deletes for real and reports each. Run `sshakku forget <key>` and that credential is gone from `cmdkey /list`, while a credential some other program saved there is still listed. |
| F40 | A session with nobody to ask — no screen, and no terminal either, which is what an `scp`, a `git` fetch or a scheduled job runs in — is never held up: SSHakku does not wait for an answer that cannot come. The key it could not load is left alone and the session carries on; a key already in the agent, or a passphrase already in your wallet, is used there exactly as anywhere else. | On an account whose key is not in the agent and whose passphrase is not saved, run something that opens no terminal of its own — `ssh host true` from a scheduled job, an `scp` — in a session with no display: it comes back on that key straight away instead of hanging, and the session log says there was nobody to ask. Save the passphrase in the wallet and the same command works with nothing typed. |

## Behaviour in the shell

| Id | Promise | How you can tell |
| --- | --- | --- |
| F10 | On success SSHakku is completely silent: nothing on stdout, nothing on stderr. | Opening a shell prints nothing, and command substitution or a script's output is never polluted. |
| F11 | Something the user should act on — a key that could not be loaded — is said once, in plain language, on the terminal. | The give-up notice appears once in the shell that tried, not on every prompt. |
| F12 | Logs record what happened and never contain a secret. | The session log shows the load decisions; grepping it for your passphrase finds nothing. |
| F30 | A command SSHakku does not recognise is answered by naming it and showing what the commands are — never by asking for a secret. Having SSHakku wired into your login shell changes nothing about that: it asks for a passphrase when `ssh` asks it to, and at no other time, whatever you type. | In a shell where SSHakku is wired in, mistype a command — `sshakku --forget`, say. You get an unknown-command error and the usage, straight away; the terminal does not go quiet waiting for you to type a secret, and nothing you type is echoed back as though it were one. |
| F43 | The lines SSHakku prints for a shell to run are printed in a language that shell speaks, and which one is what you asked for rather than something guessed from the operating system. `--shell=powershell` prints PowerShell — `$agent_sock = '…'`, `$env:SSH_ASKPASS = '…'`; no flag, or `--shell=posix`, prints the Bourne assignments every POSIX shell reads, so one binary serves a PowerShell session and a Git Bash session on the same machine. Whatever is in a path survives the quoting of either language, including the characters that language would otherwise read as the end of it. A dialect SSHakku does not have is refused by name, with nothing printed for a shell to run — never answered in the wrong language. | In PowerShell, `sshakku shell-init --shell=powershell \| Invoke-Expression` leaves `$agent_sock` holding the socket path, and `sshakku askpass-env --shell=powershell \| Invoke-Expression` leaves `$env:SSH_ASKPASS` naming the helper. Run either with no flag and you get the `agent_sock='…'` form, which `eval` sets in bash — from Git Bash on that same Windows machine, that is still the one you want. Do it from an account whose home is `C:\Users\O’Brien`, curly apostrophe and all, and the path arrives whole. Ask for `--shell=fish` and you are told fish is not one of them, and given no lines at all. |
| F21 | Nothing SSHakku waits on can hold your shell up with no end — neither a program it runs nor a secret store it calls into directly: one that neither answers nor fails is given up on, and you are asked on the terminal instead. How long to wait is configurable, separately for something expected to answer on its own and something that is waiting on you. | With a wallet that hangs rather than fails (locked, with an unlock prompt nobody can answer; a keychain waiting for someone to approve access), the shell still comes back and `ssh` asks you for the passphrase instead of waiting forever. |

## Diagnostics

| Id | Promise | How you can tell |
| --- | --- | --- |
| F13 | `sshakku doctor` explains the current agent and key situation, including problems SSHakku cannot fix by itself. | Break something (kill the agent, leave a stale socket) and the report names it. |
| F48 | Something this build of SSHakku has no implementation of on your platform is not a failure of the session that met it. A login shell opens normally and silently, the session log records the missing piece as a fact rather than as an error, and `sshakku doctor` names what is absent instead of telling you a new login shell will put it right. What SSHakku cannot do here, it does not promise. | On Windows this build draws no passphrase dialog of its own: `sshakku config` offers `gui_prompter` nothing to name but `auto` and `none`, so no dialog is promised there and none is silently in force. Sitting at the machine you are asked on the console, straight away, rather than left waiting on a window nobody will draw — and the login shell opens normally and silently all the same: the keys it can add, it adds, and the session log records the absent piece as information rather than as an error. |
| F14 | `sshakku doctor --fix` repairs what it reports as fixable, and says what it did. | After `--fix` the same report comes back clean. |
| F15 | `sshakku doctor --test-backend` proves the configured secret backend can store, look up, and delete for real. | It performs a real round trip and reports pass or fail per operation. |
| F25 | `sshakku doctor` names the wallet it would use, and how it would reach it, and tells you when something that wallet needs is not there — without touching a single stored passphrase to find out. | Configure a wallet whose tool is not installed: the report names the wallet and says which piece is missing, instead of leaving you to discover it the next time `ssh` asks for a passphrase. |
| F31 | `sshakku doctor` shows the environment it is actually running in — every variable SSHakku reads, each with its value, or `unset` where you have set none. A shell that is wired wrongly can be read off the report instead of guessed at, and a setting you exported and forgot is visible next to the one it is overriding. Secrets are the exception, and the report says only whether they are set: what you paste into a bug report must never be a way of publishing one. | Run `sshakku doctor` in a shell SSHakku is wired into: `SSH_ASKPASS` and `SSH_ASKPASS_REQUIRE` are listed with the values that shell has, alongside any `SSHAKKU_*` setting you exported. Now export `SSHAKKU_HANDOFF_TOKEN` to a value you would recognise and run it again: the report tells you the variable is set, and that value appears nowhere in it. |
| F41 | `sshakku doctor`'s plain report is a look, not an action. It always arrives, and it arrives whole enough to send to someone: a wallet that is absent, not running, or no longer answering becomes a line in the report saying so — never a report that fails to come, never a wait with no end, and never a change to anything it looked at. What may act is what you ask for by name: `--test-backend` proves a wallet with a real round trip, and `--fix` is the one allowed to write. | Point the configuration at a wallet whose daemon is not running, or stop one while the report is being made: the report still prints, and prints promptly, saying what it could not determine rather than leaving the line out. Afterwards the wallet holds exactly what it held before — the same compartments, the same entries. |
| F42 | The compartment your wallet keeps SSHakku's passphrases in is something SSHakku can make for you, rather than something you have to go and arrange yourself. Where the report says it is not there, it also says whether this session could make one, and `sshakku doctor --fix` makes it and tells you what it made. Where it cannot be made — a session with no screen, when the wallet will only make one through a dialog — `--fix` says so, and says what it would take, and leaves the wallet holding exactly what it held before rather than half of something. | On a desktop session whose wallet has no SSHakku compartment yet: `sshakku doctor` says the compartment is not there and names `--fix` as what makes it; `sshakku doctor --fix` reports having made it, and the report it prints afterwards lists the compartment as present. Run the same command over SSH with no display: it says the compartment cannot be made there and what it would take, the report still comes back, and the wallet holds no new compartment. |

## Configuration

| Id | Promise | How you can tell |
| --- | --- | --- |
| F16 | The key lifetime in the agent is configurable, and a key really is dropped when it elapses. | Set a short lifetime; `ssh-add -l` stops listing the key once it passes. |
| F17 | Which secret backend is used can be chosen, and an unavailable one degrades to prompting rather than failing the shell. | Point the configuration at a backend that isn't running: the shell still opens and you are prompted. |
| F18 | Per-key policy is honoured: a key can be excluded from automatic loading, or from being stored in the wallet, without losing the other behaviour. | An excluded key is never auto-loaded but can still be added on demand; a non-stored key works in-session and leaves no wallet entry. |
| F22 | KeePassXC can be chosen as your wallet by name, on every OS SSHakku supports. How SSHakku reaches it is not something you have to state: the same setting works on Linux and on macOS. | Put `secret_backend = "keepassxc"` in the configuration on either OS: your passphrases are saved into, and read back from, your open KeePassXC database. |
| F26 | Only wallets your operating system actually has can be chosen. Naming one that cannot exist there is treated as a mistake in your configuration — SSHakku says so and carries on with your platform's own default — rather than as a wallet that is merely missing a piece you could go and install. | Put `secret_backend = "secret-service"` in the configuration on macOS: the session log says the value is not valid there, `sshakku doctor` names the keychain, which is the wallet actually in use, and never asks you to supply a D-Bus session bus that no Mac has. |
| F27 | SSHakku only ever touches entries it put there itself. Where your wallet also holds other applications' secrets, forgetting everything forgets everything *of SSHakku's*: nothing else is read, listed or deleted, whatever the wallet would have let SSHakku do. | Keep an unrelated secret in the same store — anything another program saved there — then run `sshakku forget --all`: your keys' passphrases are gone and that entry is still exactly where it was. |
| F32 | The name SSHakku's entries carry in your wallet is yours to choose, and every operation moves with it: what a first prompt saves, what a later shell reads back, and what `sshakku forget` removes always agree on one name. No configuration you can write leaves a passphrase stored under one name and looked for under another. | Set `service_prefix` to a name of your own and load a key: the wallet entry carries that name. `sshakku forget <key>` then removes that entry and the next load asks for the passphrase again; `sshakku forget --all` removes everything stored under the name you chose, and nothing stored under any other. |
| F33 | The compartment SSHakku keeps its entries in is yours to name — the collection it makes in your Linux wallet, the group it makes in your KeePassXC database — and it creates that one and uses no other. What it will not do is move into a compartment your desktop already keeps for itself: a name belonging to your desktop's own wallet is refused. Everything inside SSHakku's compartment is SSHakku's to delete, and that is a promise it can only keep about a compartment it made itself. | Set `secret_container` to a name of your own and load a key: the passphrase is in a collection by that name, and there is none named `sshakku`. Now set it to `default` and load again: the session log says the name is refused, your keys go to SSHakku's own collection, and every secret your desktop keeps in its login keyring is still there. |
| F34 | Which files SSHakku treats as your keys is yours to state: the directory it looks in, and the names it recognises there. Say so and a key called `work-github` is loaded exactly like `id_rsa`, and `sshakku doctor` reports the directory it really read rather than the one it would otherwise have assumed — it names that directory even when it recognised no key in it, which is exactly when a name rule matching nothing is indistinguishable from a directory you did not mean. A directory you named that is not there is a mistake and is reported as one — an account that simply has no `~/.ssh` is still no error. What no configuration can do is make SSHakku offer something that is not a key of yours: public keys, and the files OpenSSH keeps for itself in that directory, are never loaded however wide the names you allow. | A passphrase-protected key called `work-github` in `~/.ssh` is ignored at login and absent from `sshakku doctor`, whose report still names `~/.ssh` as the directory it read. Add `key_patterns = ["id_*", "work-*"]` and open a shell: it is asked for once, loaded, and listed. Point `key_dir` at a directory of your own and the keys loaded and reported are the ones in it, under its name; widen the patterns to `["*"]` there and `known_hosts`, `config` and the `.pub` files are still not treated as keys; point `key_dir` at a directory that does not exist and the session log says so. |
| F35 | What SSHakku is configured to do is one command away. `sshakku config` prints every setting, the value in force, and where that value came from — the built-in default, an environment variable, `config.toml`, or the drop-in that overruled them — so a configuration split across a directory is not something you have to merge in your head. A value SSHakku refused appears there too, instead of only in a log you had no reason to open, and the files it read are named in the order it read them. Nothing printed is a secret: a passphrase is never a setting, and what you see is what you wrote. | Set `key_lifetime` in `config.toml` and again in `config.d/50-work.toml`, then run `sshakku config`: one value is shown as being in force, beside the name of the file that set it. Export `SSHAKKU_KEY_LIFETIME` and run it again: the value follows, and the environment is named in the file's place. Now write a `key_lifetime` no duration parser could read: the report says that value was refused and shows the one in force instead, without your having to open the session log. |
| F36 | `sshakku config --edit` opens your own `config.toml` in your editor, creating it from a commented template if you have none. That file and no other: the drop-ins under `config.d/` may be somebody else's to maintain, and SSHakku does not open them on your behalf. When you close the editor it tells you what you would otherwise have discovered at your next login — a file that can no longer be parsed, a value in it SSHakku will not use, and any key it sets that a drop-in or an exported variable decides instead. | With no configuration at all, `sshakku config --edit` opens a file listing every setting, and what you uncomment in it is what `sshakku config` reports afterwards. Set `key_lifetime` in `config.d/50-work.toml`, then edit that same key: closing the editor tells you the drop-in still wins, and `sshakku config` agrees with it. Write a duration no parser could read and you are told that too, before you have gone anywhere. Leave a stray bracket behind and you are told there and then, instead of finding at the next login that the whole file had been discarded. |
| F37 | Which dialog asks you for a passphrase is yours to choose, and by default it is one your own desktop provides — you do not have to be running any particular desktop to be asked in a window rather than in a terminal you may not be looking at. `gui_prompter` names a different one, or refuses a dialog altogether so that you are always asked on the terminal, even sitting at the screen. Naming a dialog is never a way to lose the prompt: one that is not installed, or that will not run, means you are asked on the terminal straight away and told which one failed — not that the key is quietly skipped. Where you have named none, a dialog that will not run is followed by the next one your desktop provides, and only then by the terminal: one that cannot draw does not take the window away from one that can. | On a graphical desktop with no KDE tooling installed at all, loading a key asks in a dialog and not on the terminal. Set `gui_prompter = "none"` and load the same key: you are asked in the terminal you started from. Set it to a program you do not have installed and you are asked on the terminal too, immediately, with the session log naming the one that could not be run. On a desktop whose first dialog is installed but cannot put a window on your screen, you are still asked in a window — the next one that can — and the session log names the one that could not. |
| F23 | If you would rather decide how KeePassXC is reached, you can say so, and SSHakku uses that way and no other. Every way of reaching it is available wherever it can work, not only on the OS where SSHakku would have picked it. | Pin the route in the configuration: the chosen one is used even where SSHakku would have picked differently — on Linux you can bypass the Secret Service entirely — and if it is unavailable you are told which one failed instead of being silently moved to another. |

## Installation

| Id | Promise | How you can tell |
| --- | --- | --- |
| F19 | Installing wires SSHakku into login shells; uninstalling removes every trace of that wiring and leaves the surrounding files untouched. | Diff the touched shell files before and after: only SSHakku's own delimited block appears and disappears. |
| F20 | The opt-in non-login wiring is additive — it never replaces or disables the login hook. | With both wired, a login shell and a plain new tab each end up with a working agent, and removing the opt-in leaves the login path intact. |
| F44 | `sshakku install` wires one shell in one command, and with nothing else said it wires **the shell you ran it from** — the PowerShell window you typed it in, the Git Bash you typed it in. You can say which outright instead, and the more precise answer wins: `--profile` names the file, `--shell-exe` names an interpreter to ask about itself, `--shell` names a kind to go and look for. Where none of those answers and nothing that started SSHakku is a shell it can wire, the install stops and asks you to name one rather than picking: a hook written into the wrong file is worse than one not written. What it did is reported as things you can go and look at — the interpreter it wired, the startup file it wrote into, and the hook that file now runs. `sshakku uninstall` takes the same selectors. | From a PowerShell window, `sshakku install` reports having wired PowerShell and names your profile; open that file and it holds one SSHakku block, running the one hook file the report also named. Do the same from Git Bash on that machine and that shell's login file gets its own. Run it where nothing in the process tree is a shell — from a scheduled task — and you are told to name one with `--shell`, with no file changed. `sshakku uninstall` afterwards leaves the file as it was before. |
| F45 | What an install writes is written in the language of the shell it is for, and spells its paths the way that shell reads one — so a single binary on a single machine can wire a PowerShell and a Git Bash without either being handed the other's file. Whatever is in a path survives the quoting of either language, including the characters that language would otherwise read as the end of it. | On Windows, install from PowerShell and again from Git Bash: the profile holds a line PowerShell runs, the login file holds a `. '/c/Users/…'` with the POSIX spelling of your home, and each shell opens afterwards with nothing printed and no error. Do it from an account whose home is `C:\Users\O’Brien` and both still open. |
| F46 | A shell that would never read what an install writes is refused **before** anything is written, and you are told what is in the way and what it would take to change — never a wiring that looks done and never runs. A PowerShell whose effective execution policy is `Restricted` or `AllSigned` does not read its profile at all, and a session in a constrained language mode cannot run a dot-sourced hook. | Run `Set-ExecutionPolicy Restricted -Scope CurrentUser`, then `sshakku install` in that PowerShell: you are told the policy in force and the command that changes it, the command exits as a failure, and your profile is exactly as it was — including still not existing, if it did not. |
| F49 | Installing puts SSHakku where your system keeps programs of that kind — under your own account for a per-account install, in the machine's program directory for a machine-wide one — and says where before you have to go looking. It is never left running from the tree you built it in: move that tree, rename it or delete it afterwards and every session you installed for goes on working, because what a login shell runs is the installed copy. Where it goes is yours to change, and uninstalling takes the program away again together with the directory it was given, if nothing else of yours is in it. | `make install-user` prints the path it is installing to and then wires that copy: on Windows `%LOCALAPPDATA%\Programs\sshakku\sshakku.exe`, on Linux and macOS `~/.local/bin/sshakku`. Delete the directory you built in, open a new session, and `sshakku doctor` still answers. Run `make install-user USER_BINDIR=…` — or `make install BINDIR=…` for the machine-wide one — and it goes where you said instead. `make uninstall-user` and the program and its directory are gone. |
| F47 | Installing leaves `sshakku` runnable by name in sessions started afterwards. Which part of the install does that is the system's answer, and the install says which: where the program is put somewhere sessions already search, there is nothing to record and you are told that rather than left to wonder; where it means recording a directory in your stored environment, the record is exact: the value is read and written in its raw form, so a `PATH` that refers to other variables goes on referring to them rather than being flattened into what they meant that day; the entry is added once, however many times you install; and uninstalling removes SSHakku's entry and leaves every other one exactly as it was. `--no-path` skips the step, and says it did. | Install, then open a new terminal and run `sshakku doctor`: it runs without your typing a path. Install a second time and read your `PATH`: SSHakku's directory is in it once. Uninstall and read it again: that entry is gone, every other one is still there, and any entry you had written as `%SOMETHING%` is still written that way. |

## Keeping this current

A behaviour that users can observe belongs here before it is implemented, not
after — see rule 21 in `CLAUDE.md`. Add the feature, give it the next free id,
then write the test that verifies it and reference the id from
[TEST-MATRIX.md](TEST-MATRIX.md). Ids are never reused: a promise that is
withdrawn is removed from the table and its id retired, so an old test or bug
report can never silently come to mean something else.
